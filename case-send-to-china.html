Turning a 12-digit CNAPS code into a four-tap dropdown

A first attempt at CNAPS-guided transfers to China landed with a thud because it pushed the work onto the sender. This is how mapping every bank and branch turned that friction into a simple, guided flow.

The problem

Sending money to China in local currency (CNY) requires a CNAPS code — a 12-digit identifier from the China National Advanced Payment System that routes a domestic RMB payment to the exact receiving bank branch. The rail genuinely needs it. With many payout providers it's resolved in the background: the provider has mapped banks and branches to their codes, so neither the business nor the customer ever sees it.

The payout processor Afriex had integrated with for the China corridor didn't offer that mapping. It required a CNAPS code with every payout but left the work of sourcing and mapping it to us. Our first attempt passed that gap straight through to the customer — the flow simply exposed the CNAPS field and asked the sender to supply the code, plus branch and postal details. It shipped, but reception was lukewarm: customers were already used to sending to China without ever touching a CNAPS code, so being asked to hunt one down felt like a step backwards. Many abandoned.

The realisation was that this mapping was now Afriex's responsibility to own, not the customer's to satisfy. If the partner wouldn't resolve CNAPS for us, we would build the mapping ourselves and hide it behind a simple flow.

The requirement wasn't the problem. Making the customer satisfy it was. The fix was to move the complexity from the sender to the product.

Old way vs. new way

✕ First attempt
  • Sender had to find the branch's 12-digit CNAPS code themselves
  • Manually enter branch name and postal code
  • Easy to mistype → failed or misrouted transfers
  • "I never needed this before" → drop-off
✓ Redesigned flow
  • Pick Bank → Province → City → Branch from dropdowns
  • CNAPS code and postal code resolve automatically
  • Nothing to source, nothing to mistype
  • Sender only adds the beneficiary's ID details

My role

I owned the recovery of this feature: diagnosing why the first release underperformed, and recognising that the gap sat with the integrated payout partner, who didn't resolve CNAPS on our behalf. I reframed the work as a data-mapping job Afriex needed to own rather than a UI tweak. I defined the reference data model (bank → province → city → branch → CNAPS + postal), scoped what the sender must still provide versus what we resolve for them, and built the PRD and interactive prototype to align engineering and design.

Approach

  1. Reframed it as a data problem we had to ownThe partner wouldn't resolve CNAPS for us, and the customer shouldn't do routing lookups — so the product had to. That meant Afriex sourcing every supported bank in China, its branches, their locations, and mapping each to its CNAPS and postal code.
  2. Built the reference dataset~148,000 branch records across 127 banks and 31 provinces, each mapped to a CNAPS code and postal code — split into selected (major) banks and other banks, and structured for cascading lookups.
  3. Designed cascading dropdownsEach selection narrows the next: choosing a bank filters provinces, then cities, then branches. Selecting the branch auto-fills the CNAPS and postal code — read-only, so they can't be mistyped.
  4. Kept only what the sender must provideSender details are already on file. The sender only confirms the beneficiary's name, ID type/number and account number, which are required for compliance and crediting.
  5. Added a clear review stepBefore sending, the resolved routing (bank, branch, CNAPS, postal) is shown for confirmation — trust without asking the customer to understand the code.

The data model

The flow is only as good as the mapping behind it. Each record ties a branch to its routing details; the app reads them as a nested lookup:
