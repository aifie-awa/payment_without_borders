Turning reconciliation from a spreadsheet into infrastructure

An automated engine that matches the internal ledger against every partner-processor settlement feed — on a unique transaction reference, with amount, currency, status and date tolerances — and routes the differences.

The problem

In most scaling payments businesses, reconciliation between the internal ledger and partner-processor settlement reports is done by hand in spreadsheets. An analyst exports the day's transactions, downloads each processor's report, and eyeballs them side by side — matching on whatever columns line up and chasing differences manually.

It doesn't scale: effort grows with every new processor, corridor and transaction. The daily close waits on a person finishing a spreadsheet, so treasury sees a true cash position late. And it hides money problems — a short settlement, a duplicate payout, a processor-side entry that never hit the ledger — surfacing them slowly, if at all. The knowledge lives in one analyst's head.

How might we reconcile the ledger against every processor feed automatically, clear what matches, and turn the differences into a worklist — so the close is fast, trustworthy and auditable?

My role

I scoped this as a product — not a script. I framed the problem, defined the requirements placed on partner processors, designed the matching logic and break taxonomy, and specified the exception workflow and success metrics. The artifacts here are the PRD, a working interactive engine, and the system architecture.

Approach

  1. Made the unique reference the contractAutomated matching is only possible with a shared key. The core requirement on every processor: accept a unique, caller-supplied reference at initiation and echo it back unchanged on every report and API record. That reference becomes the single join key between our ledger and theirs.
  2. Defined the data contract per processorEach processor delivers a complete daily report — a file over SFTP or a pull from a transactions API — with documented fields, a stable status vocabulary, and fees itemised separately from principal.
  3. Designed tolerance-based matchingMatch exactly on the reference, then validate the pair on amount (within a % tolerance for FX rounding), currency, status, and settlement date (within a day-window). Legitimate rounding clears automatically; real differences don't.
  4. Built a break taxonomy, not a binaryEvery non-match is typed — amount, currency, status, date-window, missing-at-processor, missing-in-ledger, duplicate — so the right team knows exactly what each break means and how severe it is.
  5. Treated exceptions as the productThe value isn't the match — it's shrinking and ageing the break queue. Each exception becomes a worklist item with an owner, an age and a resolution state, with recurring patterns feeding back into tolerances or partner conversations.

How matching works

Matching is a deterministic sequence applied per reference — each step either clears the pair or produces a typed break:

1. Join on reference (present both sides?) → 2. Duplicate check → 3. Currency (identical?) → 4. Amount ± tolerance → 5. Status & date-window → 6. Clear or route to the exception worklist.

Tolerances are configurable per engine and overridable per processor or corridor — some rails settle T+2, some price with a different rounding convention.

System architecture

Sources → ingestion → normalization → matching engine → cleared ledger + exception worklist + dashboard. A deliberate principle: feed the shared money-movement layer that treasury and other product lines consume — don't build a parallel one. Open full screen ↗
